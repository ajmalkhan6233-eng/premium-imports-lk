# Premium Imports LK — Full Professional Audit

**Scope:** Premium Imports LK (Node.js/Express, JSON storage, localhost:3005 / LAN). Read-only, findings-only pass. No code, data, or config was modified. Bathco was not touched or referenced.

---

## Executive Summary (Chair / CTO)

The application works, and several things are done *well* for a small local system: atomic file writes (`saveData()` temp-file-then-rename), daily backups, consistent ledger recomputation (vendors/lenders/customers all recompute balance from source totals rather than accumulating drift), a genuinely hard-gated WhatsApp escalation check, and a wake-phrase that cannot be spoofed by a customer. Those controls are real and confirmed working.

However, the system has one architectural gap that undermines almost everything else: **the server has no authentication, no authorization, and no validation on its data API.** Every business rule this audit was asked to check — discount limits, stock checks, sequential numbering, role restrictions, PIN protection — is implemented only in browser JavaScript. A single unauthenticated `fetch()` call (from a phone on the same WiFi, or from the public `/shop` page's own network tab) can read or overwrite the entire business database, including staff PINs and bank account details used for customer payment QR codes.

**Top 5 issues, ranked:**

1. **No authentication/authorization on `/api/data/:key`** (Council 1). Anyone with network access to the server — including anonymous visitors to the public storefront — has full read/write access to every collection: bills, customers, vendors, loans, WhatsApp conversations, and `settings` (which contains plaintext staff PINs and bank account details). This is the root cause of most of what follows.
2. **Bank details are writable with no authentication** (Council 1). Bank account name/number shown on the QR code for bank-transfer payments (in-store and storefront) can be silently changed by anyone who can reach the server — a direct path to redirecting real customer payments.
3. **Storefront order price is trusted end-to-end into a real bill** (Council 3). The price a customer's browser reports for a cart item is never re-checked against the actual product price, either at order-placement or when staff "Confirm & Bill" it.
4. **Numbering and concurrent writes are not safe under real multi-device use** (Council 2). Order numbers use array length (not a durable counter), and every write to any collection is a non-atomic full-array replace — two devices acting near-simultaneously (two online orders, a POS sale racing a storefront order, two WhatsApp customers texting in together) can silently drop one side's data or produce duplicate bill/GRN/order numbers.
5. **No process supervision** (Council 5). `node server.js` runs directly with no auto-restart (the README itself notes PM2 "is a future upgrade, not set up here"). One unhandled crash or a closed console window takes down the POS and the public storefront until someone notices and manually restarts it.

None of this requires an external attacker to matter day-to-day: the biggest practical risk today is *accidental* data loss from ordinary concurrent use (two staff/devices, or a customer ordering while a sale is being rung up), not a hypothetical intruder. The security gaps become urgent the moment the LAN boundary is ever crossed (a misconfigured router, a guest on the WiFi, a firewall prompt answered "Allow on Public networks").

**Sign-off required before any fix is applied** (touches money, customer data, or auth):
- Adding authentication/authorization to the `/api/data/:key` API and the login flow.
- Removing plaintext PINs from the pre-login `settings` payload / changing how PINs are stored.
- Moving discount, stock, and pricing validation server-side (affects Sell, Storefront, GRN, Orders).
- Any change to bill / GRN / order numbering (affects continuity with existing paper/invoice numbers).
- Adding locking/versioning to `data.json` writes (affects every screen that saves).
- Changing the WhatsApp escalation keyword list or barge-in handling (customer-facing behavior, financial/complaint risk).
- Firewall / router / LAN-exposure verification — this requires hands-on access to the shop machine and network, which this audit could not perform; log as open until manually confirmed.

## Council 1: Security & Access
**Personas: CISO / Penetration Tester + Backend Security Engineer**

### Findings
| # | Severity | Area | Finding | Evidence (file:line) | Recommendation |
|---|----------|------|---------|----------------------|-----------------|
| 1.1 | CRITICAL | API auth | No authentication or session check exists on any `/api/data/:key` route. Login (PIN check) and admin/staff gating are implemented entirely in browser JS and are trivially bypassed with a direct HTTP call. | server.js:151-170; app.js:218-233 (PIN check), app.js:303-307 (`goTab` admin gate) | Add a server-side session/token check on every `/api/data/:key` request; re-derive role from the server session, never trust the client for authorization. |
| 1.2 | CRITICAL | Secrets exposure | Staff PINs are stored in plaintext in `settings.users` and are fetched to the browser as part of the normal `GET /api/data/settings` call made *before* login (to populate the user picker), so the full PIN list is visible to any client that loads the page or calls the API directly. | server.js:23-26 (default users incl. plaintext pins); app.js:174-176 (settings fetched pre-login); settings.js:259-288 (PIN set/reset) | Never send PINs to the client; verify PIN server-side and return only a session token. | 1.3 | CRITICAL | Financial tampering | `settings.bankDetails` (account name/number used to generate payment QR codes on bills and the storefront) is writable via the same unauthenticated `PUT /api/data/settings`. | server.js:159-170; settings.js:151-160 | Same fix as 1.1 — once writes require auth, this closes automatically. | 1.6 | MEDIUM | Transport security | All traffic, including PINs and financial data, travels as plaintext HTTP over WiFi — no TLS. | server.js:310 (`app.listen`, no https) | Low cost/benefit to fix on a LAN-only local tool once auth exists; note as accepted risk or add a self-signed cert if the threat model changes. |
| 1.7 | LOW | Error disclosure | No custom error-handling middleware is registered; Express's default handler is used, which can include stack traces (file paths) in non-production mode. | server.js (no `app.use((err,req,res,next)=>...)` found) | Add a minimal error handler that returns a generic message; set `NODE_ENV=production`. |

## Council 2: Data Integrity
**Personas: Database/Systems Architect + Chartered Accountant**

### Findings
| # | Severity | Area | Finding | Evidence (file:line) | Recommendation |
|---|----------|------|---------|----------------------|-----------------|
| 2.1 | CRITICAL | Order numbering / lost writes | Storefront order numbers are derived from `currentOrders.length + 1` (not a durable counter), read and written as a full non-atomic array. Two customers checking out around the same time can get the same order number, and the second `PUT` silently overwrites the first — one customer's order vanishes with no error to either party. | public/shop/shop.js:276-279 | Generate order numbers the same way bills/GRNs do (`nextNumber`, server-side once auth exists), and make the append operation atomic server-side rather than client read-modify-write. |
| 2.2 | CRITICAL | Concurrent write safety | Every `/api/data/:key` write replaces the entire array/object with whatever the client currently holds — there is no locking, versioning, or merge. Any two concurrent writers to the same key (two POS devices, POS + storefront, two WhatsApp conversations) will have one overwrite the other. | server.js:159-170 (whole-value replace); whatsapp-bridge/conversations.js:26-28; whatsapp-bridge/index.js:96-101 | Move mutations server-side as targeted operations (e.g. `POST /api/bills`, `POST /api/customers/:id/ledger`) instead of "fetch whole array, mutate, PUT whole array back," or add optimistic-concurrency version checks. |
| 2.3 | HIGH | Sequential numbering under concurrency | Bill and GRN numbers come from `STATE.settings.counters`, incremented in the browser and persisted via the same last-write-wins `saveKey('settings')` as everything else. Two devices completing a sale/GRN close together can compute and save the same "next" number. | app.js:109-115 (`nextNumber`); sell.js:366-368, sell.js:396; grn.js:355 | Move counter increment to the server as an atomic operation; this is the only correct way to guarantee true sequentiality across devices. |
| 2.4 | HIGH | Cost-basis / profit accuracy | `product.costPrice` is overwritten with the latest GRN cost only (server.js/grn.js:362: `p.costPrice = it.cost`) rather than tracked as FIFO/weighted-average — even though the codebase already builds FIFO batch data elsewhere (for "Days in Stock"). Any sale made after a vendor price change attributes the *new* cost to units that may actually have come from an older, cheaper (or pricier) batch, which flows directly into the Net Profit report. | grn.js:360-363; app.js:398-432 (`computeProductAgingDates`, FIFO batches already modeled); reports.js:57-64 (Net Profit uses `it.cost`) | Reuse the existing FIFO batch tracking to assign the correct historical cost per unit sold, or explicitly document that Net Profit is an approximation and accept the known variance. |
| 2.5 | MEDIUM | No schema validation on writes | `PUT /api/data/:key` accepts any JSON value for `value` with no shape/type check. Writing a wrong-typed value for any key (e.g. a string where an array is expected) corrupts that collection in `data.json` and breaks every screen that reads it, with no server-side guard. | server.js:159-170 | Add minimal shape validation per key (e.g. "must be an array" for collections) before accepting a write. |
| 2.6 | LOW | Corrupt-file recovery | If `data.json` becomes unparseable, `JSON.parse` throws during server startup with no automatic fallback to the daily backups already being written to `backups/`. | server.js:92-93 (load), server.js:126-136 (backups exist but aren't used for recovery) | On parse failure, log clearly and optionally auto-load the most recent file from `backups/` rather than refusing to start. |
| 2.7 | — (positive control) | Crash-safety of single writes | `saveData()` writes to `data.json.tmp` then renames over `data.json`, so a crash mid-write cannot leave a half-written file. Confirmed correct as implemented. This does **not** address the concurrent-writer problems above (2.1–2.3), which are a different failure mode. | server.js:138-142 | No action — keep as-is. |

## Council 3: Business Logic
**Personas: Retail Operations Auditor + Chartered Accountant**

### Findings
| # | Severity | Area | Finding | Evidence (file:line) | Recommendation |
|---|----------|------|---------|----------------------|-----------------|
| 3.1 | CRITICAL | Truth divergence | All business rules — discount clamping, stock checks, non-negative price enforcement — are enforced only in the browser. Because the API performs no validation (Council 1/2), any direct API write can produce a bill with a negative total, a discount exceeding the subtotal, or stock driven negative, completely bypassing the UI's safeguards. | sell.js:23-31 (discount clamp, client-only); sell.js:346-364 (stock checks, client-only); server.js:159-170 (no server check) | Re-implement these checks server-side once the API accepts write requests with a defined shape; treat the client-side checks as UX only. |
| 3.2 | CRITICAL | Storefront price integrity | An online order's price is entirely client-supplied at add-to-cart time and never re-validated against the authoritative product price — neither when the order is placed (`shop.js`) nor when staff convert it to a real bill via "Confirm & Bill." | public/shop/shop.js:134-144 (cart price set from client-held product list), shop.js:261-279 (order submitted with client price, no server check); public/app/sell.js:537-563 (`ord-confirm` builds the real bill directly from `o.items`, including `it.price`, with no cross-check against `STATE.products`) | When confirming an order into a bill, re-price every line from the current `products` table (or reject if it has drifted) rather than trusting the stored order price. | 3.3 | MEDIUM | GRN input validation gap | GRN line quantity/cost fields only guard against `0`/`NaN` (`parseInt(...) \|\| 1`, `parseFloat(...) \|\| 0`), which does **not** catch negative numbers — unlike the Sell cart, which explicitly blocks negative prices. A negative GRN qty or cost silently corrupts stock counts and the vendor ledger. | grn.js:309-312 (`gq-add` handler); grn.js:337-343 (`ge-save` edit handler); compare sell.js:186-187 (explicit `< 0` guard) | Add the same explicit `< 0` rejection used in sell.js to all GRN qty/cost inputs. |
| 3.4 | LOW | Below-cost sales visibility | Cart line price is freely editable with no floor relative to the item's cost price, and nothing flags a below-cost sale on the receipt, in the bill record, or in reports. | sell.js:183-190 | If intentional (e.g. for write-offs/promotions), consider a soft warning at sale time and/or a flag on the bill so it's visible in the Net Profit report rather than silently reducing margin. |
| 3.5 | — (positive control) | Discount math | `computeSellTotals()` correctly clamps the discount to `[0, subtotal]`, so the Sell-screen UI path can never produce a negative total, and it's the single source used for both the on-screen total and the saved bill. GRN totals are clamped the same way. Vendor/lender/customer balances are recomputed from source totals on every save rather than accumulated, avoiding drift. | sell.js:23-31; sell.js:377; grn.js:7-9; vendors.js:137-138; loans.js:166-167, 195-196 | No action — keep as-is; this logic should be the reference when the same checks are added server-side. |

## Council 4: WhatsApp Agent

### Findings
| # | Severity | Area | Finding | Evidence (file:line) | Recommendation |
